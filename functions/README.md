# Bite serverless checkout

This code runs in Firebase Cloud Functions and uses the existing Firestore collections. No separately hosted application server is required. The current slice supports **cash on delivery only**. Card collection, Stripe customers/intents, verified webhooks and payment reconciliation are the next commerce slice.

## Callable contract

Both functions run in `us-central1`, require Firebase Authentication and derive ownership from `request.auth.uid`. The Flutter `cloud_functions` SDK carries the authenticated callable request. No UID, currency, price or order status supplied by the client is trusted.

### `quoteCart`

Request: `{cartId, addressId, requestId}`. IDs are nonempty strings without `/`, at most 200 characters; requestId is a UUID-shaped 36-character string generated by the client.

Response: `{quoteId, currency, subtotalMinor, deliveryMinor, platformFeeMinor, totalMinor, expiresAt}`. Currency is PKR and all amounts are integers in minor units. `expiresAt` is epoch milliseconds. Quotes expire after five minutes.

The function checks cart ownership and an address under the caller's `UsersDB/{uid}/addresses` collection; reads current products and the restaurant; rejects empty/oversized carts, mixed restaurants, closed restaurants, unavailable products, invalid quantities/options and invalid monetary values. Cart snapshots are not price authorities. Existing catalog business IDs and document-ID fallback are supported.

`PLATFORM_FEE_MINOR` is a deployment parameter with default `2000` (PKR 20, matching the old app). Delivery fee comes from the restaurant record. Neither fee can be overridden by the client. The catalog currently has no option surcharges, tax or delivery-zone schema; those policies must be defined before offering such features.

A quote is stored at `CheckoutQuotes/{uid}_{requestId}`. Repeating the same unchanged request returns that quote. Reusing its ID after expiry, changes or use requires a new review.

### `placeCashOrder`

Request: `{quoteId}`. Response: `{orderId}`.

The transaction verifies owner/expiry, recalculates using current cart/catalog/address data, and compares a fingerprint of quantities, variants, prices, fees and address text. It atomically writes `OrdersDB/{quoteId}` and its `Items`, removes the quoted cart lines and marks the quote used. The parent cart is retained. A changed cart/price/address is rejected rather than silently repriced at submission.

Orders use `paymentMethod: onCash`, `isPaid: false`, `orderStatus: received`, integer totals plus the legacy major-unit `totalPrice` field, and a delivery-address text snapshot. Repeated or concurrent successful submissions return the same order, including after quote expiry when the order already exists. An uncertain client response retains the quote for retry; order history can recover a completed order after app restart.

Typical callable errors are `unauthenticated`, `permission-denied`, `invalid-argument`, `failed-precondition` (review needed) and `internal` (retry/reconcile). Internal exception contents are not exposed to the app.

## Local checks

Install dependencies with `npm ci --prefix functions`. `npm --prefix functions test` runs pricing tests and skips the emulator tests when no emulator is configured.

Run the actual transaction-handler tests against an isolated Firestore emulator:

```sh
npm exec --yes --package firebase-tools -- firebase emulators:exec --only firestore --project demo-bite-checkout --config functions/test/firebase.json 'npm --prefix functions test'
```

The tests require a local emulator host and a `demo-` project ID. They exercise the real Admin SDK and Firestore transactions through callable handlers, including concurrent requests, ownership failures, invalidation and retries. They do not exercise deployed callable token transport, App Check, production security rules, Stripe or a physical device. The test rules deny all client access; Admin SDK transaction tests bypass client rules by design.

## Deployment and release prerequisites

`firebase.json` registers the `checkout` functions codebase; Node 22 is the declared deployment runtime. Local tests were executed with Node 24. No production deployment was performed.

Before deployment/release:

1. Confirm the Firebase project, region, billing configuration, fee/currency and merchant policies. Use Firebase tooling with the intended project explicitly selected.
2. Merge and test the following requirements in the authoritative Firestore rules (this checkout does not include the production rules). **Do not deploy the test `deny.rules` file as production rules.**
   - Clients must not read/write `CheckoutQuotes` or create orders/paid statuses. Only trusted server/admin operations may do so.
   - Users may read only their own orders and order items. Restrict cart and address access to their owners.
   - Prices, fees, availability and restaurant status must be writable only by trusted merchant/admin code; otherwise server calculations can still be fed attacker-modified catalog data.
   - Audit broad wildcard grants. Migrate legacy client order cancellation/status/history deletion to trusted server operations before enforcing the final rules.
3. Configure and test Firebase App Check before enforcing it on these functions. Authentication is checked in code; App Check enforcement is not enabled in this slice.
4. Verify quote→order on staging from the Flutter app, including reconnect, app termination and another account; confirm retention/cleanup for quotes and abuse controls.
5. Only then deploy the reviewed codebase using the intended Firebase project and run device validation.

The new checkout does not offer card payments. Legacy saved-card management still contains client-side Stripe operations and must be migrated before release. Remove/rotate any real secret previously shipped to clients; no credentials were rotated here. The existing address picker and map editor also remain part of the remaining UI migration.

## References and tool limits

Implementation follows [Firebase callable functions](https://firebase.google.com/docs/functions/callable) and [Firebase environment configuration](https://firebase.google.com/docs/functions/config-env). A future card flow must follow [Stripe PaymentIntent lifecycle guidance](https://docs.stripe.com/payments/payment-intents) and verify payment completion server-side.

The installed Postman CLI did not support `postman status`; no Postman workspace was initialized or modified. Local contracts and Flutter/Node/Firestore-emulator evidence are retained in this repository instead.
